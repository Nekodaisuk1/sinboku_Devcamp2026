# Service evaluation

## 評価の基準

対象は、ゲーム・料理・ギター・海の生き物が好きで、他人に相談する前に自分で試したい中高生。点数は開発者による操作検証の自己評価であり、本人によるユーザーテストの評価ではない。

合格基準は各軸4/5以上かつ合計24/30以上。未実装や未検証の動線を、他の項目の高得点で相殺しない。

- 1: 説明・固定例のみ
- 2: 一部の操作のみ可能
- 3: 主動線は動くが、重要な制約・未検証箇所が残る
- 4: 主動線と境界ケースを実装し、端末幅を含めて検証済み
- 5: 本人に近い対象者の利用観察でも妥当性を確認

## 次の改善

1. スマホの地図を、横に探し回らず興味の分岐と近領域が理解できる表示にする。選択中の文脈を保つ。

「保護者と共有できます」という表示が、対象者にとってこのサービスを使用不可能にする、という前提をコードに反映した。Build 07〜13では共有機能が実装され、気になるページの2番目のタブに置かれていた。現在は`FAMILY_SHARING_ENABLED = false`で導線ごと外れており、起動時に共有APIも呼ばない。

### 次の改善

2. 利用者の地域を尋ねずに絞り込む方法の検討。現在は都道府県の入試案内へ送るところで止まっている。
3. 保留可能期限を、自治体の実際の入試日程と接続する。現在は一般的な目安。

5. 共有機能のコードを残すか撤去するかの決定。残す限り、フラグを戻せば矛盾が再発する。

### Build 14 との一番大きな違い

Build 14 は「保護者と共有できます」という表示が対象者にとって使用不可能の理由になる、という前提をコードに反映した。Build 19 は **「読んで終わるアプリは、対象者の分類では縄跳び側にいる」**という前提を反映した。

料理は皿が出る。ギターは音が出る。縄跳びは何も出ない。続いたものと続かなかったものの差は意志ではなく、やったら何かができあがるかにある。だから蓄積物をメモテキストから「やったこと」に変えた。これが効くかどうかは、実装では判定できない。

### 次の改善

1. **対象者本人（または近い条件の中学生）による利用観察。** 全軸で5に届かない理由はこれ1つで、Build 05 から変わっていない。段階を進める前に一度挟むこと。特に「7年が圧迫になっていないか」「空欄が未完了タスクに見えていないか」は机上では判定できない。
2. 中3が今週やれる活動を、ゲーム・料理・音楽の各領域で3件ずつ実在情報として調べる。件数を増やすより年齢の適合を優先する。
3. 地域の中間状態を抜ける。高校の段から実在校名を外すか、地域指定を任意で受けるかを決める。
4. 領域ごとの掲載件数を画面に出す。等量に見せて裏切るより、薄い場所を先に言う。
5. 動詞5つが正しい粒度かを、観察で確かめる。外していれば、これは Build 18 の「8領域」と同じ失敗になる。

### Build 19 との一番大きな違い

Build 19 は「時間を縦に並べた」。Build 20 は「時間を縦に置いて、横を空けた」。

空けた横に何も意味を持たせなかったのが判断の中心である。横を分野や確信度に使えば情報密度は上がるが、置いた位置をアプリが解釈することになり、この対象者の中心的な行動原理（勝手に何かをされることを嫌う）に反する。かわりに、**本人が置いた位置から線が伸びて、その線が合流する場所だけが情報になる**構造にした。
